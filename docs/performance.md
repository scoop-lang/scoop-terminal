# Terminal 性能测量

固定基线为 `d990f72`，M5 为 `89cdabb`。本节先记录优化前的数据，后续结果按提交追加。原始关键指标保存在 [performance-baseline.json](performance-baseline.json)。这是一次本机采样，不能当作跨机器性能保证。

## 运行方式与边界

```sh
python3 tools/benchmark_terminal.py \
  --scoop ~/.scoop/bin/scoop --sysroot ../scoop/sysroot \
  --baseline d990f72 --label working --output /tmp/terminal-performance.json
```

每个场景是单独的 release 测试进程，普通 `scoop test` 不执行这些 `@Ignore` 基准。脚本把旧提交导出到自动清理的临时目录，补入同一测量代码与字体、时间库依赖，以及旧版缺少 `Terminal.close()`、颜色主题、reading 和选择数组的 API 适配。旧字形缓存仅增加 miss 计数，不改变查找和排版。不会切换当前工作目录的 Git 分支。`--baseline` 只接受本设计固定基线；`--cases` 可以只运行受影响场景，`--repetitions` 可增加独立进程样本。

环境：Apple M3 Ultra、512 GiB RAM，macOS 27.2.1 arm64；Scoop `0.0.0-dev.20261126`，编译器 `bb295704db1ae4592a065fa424dead159cfd5d84`，开发 sysroot 包含 Scoop main `a1eac393e`。同一轮先运行基线，再运行 M5；没有同时运行其他测试或构建任务。

核心 feed 测量每次约 8 KiB，共 256 次约 2 MiB，历史上限 10000。耗时只包含 `Terminal.feed()`，包含它产生的解析、屏幕更新、快照与变化集；不包含 PTY、文字排版或窗口提交。分配与 RSS 来自进程退出时的 `SCOOP_GC_STATS=1`，含测试初始化及清理。`allocated_bytes` 是累计托管分配，`peak_rss_bytes` 是整个测试进程峰值，不能当作图片 GPU 显存或可达对象大小。

M5 现在处理字素、逻辑行、共享快照、跟踪以及图形生命周期，和旧版本的工作量并不完全相同；但上述新增成本不能作为不优化的理由。当前优先检查短行后部的空单元、快照复制和 reflow 分配。

10 万行历史以 `log\r\n` 填满，抽取 32 个分散行号，查找 2048 次。基线累计查找 119.58 ms，M5 为 0.15 ms；M5 已使用索引。该场景 M5 峰值 RSS 6716.0 MiB、累计分配 3598.9 MiB，显示存储空单元仍有很大成本。

reflow 场景保留 10000 条 62 字符日志，在 40 与 240 列之间往返 12 次。M5 的 24 次 resize 累计 4181.30 ms，p95 为 231.85 ms，分配 12683.3 MiB，峰值 RSS 2871.9 MiB。基线只裁剪可见网格，没有正文 reflow，其 3.08 ms **不是等价功能的性能对照**，仅保留为旧行为记录。

这轮核心数据不包括字体/DPI、帧延迟、事件到 Accepted 帧、搜索、图片资源或其他平台；对应测量在后文分别记录，不用核心 feed 耗时替代真实窗口指标。

## 隐式空白与共享行

行尾默认／样式空白不再展开为完整单元数组，发布的历史行和当前可变模型共享冻结前缀，下次编辑才复制。所有物理列仍可索引，显式空格、宽尾格、擦除颜色和旧快照保持原语义。相同 8 个场景的结果保存在 [performance-compact.json](performance-compact.json)。

| 场景 | M5 总耗时 ms → 当前 | M5 分配 MiB → 当前 | M5 峰值 RSS MiB → 当前 |
| --- | ---: | ---: | ---: |
| ASCII 120×40 | 590.37 → 574.95 | 1218.8 → 1468.0 | 1456.9 → 361.4 |
| ASCII 240×80 | 840.34 → 567.12 | 2096.0 → 1497.8 | 2086.0 → 376.2 |
| SGR 120×40 | 560.41 → 406.10 | 1322.4 → 983.1 | 1437.8 → 246.2 |
| SGR 240×80 | 844.16 → 409.37 | 2335.0 → 984.0 | 2075.3 → 245.0 |
| Unicode 120×40 | 540.79 → 455.93 | 1235.4 → 993.2 | 1260.6 → 235.8 |
| Unicode 240×80 | 843.80 → 450.57 | 1993.0 → 994.1 | 2049.6 → 231.0 |
| 历史 10 万行定位 | 0.15 → 0.16 | 3598.9 → 756.7 | 6716.0 → 213.8 |
| reflow 1 万行 × 24 次 | 4181.30 → 3693.91 | 12683.3 → 8656.3 | 2871.9 → 594.3 |

120 列 ASCII 的累计分配上升约 20%，来自展开前缀的增长／冻结路径，不能把 RSS 下降说成所有分配均减少。reflow 仍有较高复制成本，下一步检查重排行构造及无跟踪对象时的开销。定位的亚微秒读数受时钟分辨率限制，不能由单次百分位推出更精确的纳秒结论。

## 重排行构造与发布所有权

重排直接构造新行，链接引用正常保留；原行编辑／跟踪在重排结束时统一迁移，不再对每个新单元执行普通覆盖路径。无跟踪对象的文字覆盖也不创建空的临时注册数组。发布时，如果可用容量最多多出 8 列，将数组所有权直接交给只读包装并清除可变引用；否则收紧前缀。下一次写入独立复制，预算始终计入实际保留容量。曾试过保留两倍容量，但 ASCII 的峰值 RSS 升高，因此没有采用该策略。

最终本轮数据见 [performance-reflow.json](performance-reflow.json)：

## 固定字体与 DPI 的绘制基准

`--cases paint120x1 paint120x2 paint240x1 paint240x2` 使用仓库 Fira Code 6.2、14 pt、禁用系统字体发现，在 120×40／240×80 网格、1×／2× raster scale 上测量。先填满屏幕，预热 16 帧，再测 192 帧，每帧增加一行含 SGR 与连字上下文的不同日志。计时包括 feed、构造／排版可见帧、CPU 光栅绘制及帧释放，字体初始化不计入耗时；分配／RSS 仍含整个测试进程。

行布局复用前的提交为 `eb48aac`，结果保存在 [performance-view-baseline.json](performance-view-baseline.json)。固定字体的连续 run 绘制已经快于旧逐格绘制，但每帧仍构造全部可见行，累计分配偏高。

| 场景 | 基线 p95 ms | 当前 p95 ms | 基线分配 MiB | 当前分配 MiB | 基线峰值 RSS MiB | 当前峰值 RSS MiB |
| --- | ---: | ---: | ---: | ---: | ---: | ---: |
| 120×40，1× | 4.295 | 1.798 | 316.1 | 684.4 | 46.2 | 80.3 |
| 120×40，2× | 4.961 | 2.220 | 316.1 | 684.4 | 54.1 | 88.0 |
| 240×80，1× | 9.176 | 3.629 | 771.5 | 1367.3 | 73.3 | 96.3 |
| 240×80，2× | 10.291 | 4.742 | 771.5 | 1367.3 | 105.6 | 128.4 |

这些是 CPU raster 工作时间，不包含实际窗口、VSync、24/96 ms 输出等待或 PTY 子进程响应。即使这里 p95 小于 16.7 ms，也不宣称端到端窗口帧延迟已经达到目标。无图片的场景上传次数固定为 0；新 run 每帧排版日志的变化部分，旧逐字缓存预热后不再新增排版，因此排版次数应结合粒度解释。

## 真实窗口的输出调度

有桌面会话时显式选择 `--cases windowFrames`，此场景不在脚本默认集合中。测试启动真实 PTY 和 960×640 logical 窗口，由子进程每次改写一行并发出唯一标题，共 120 次；子进程有约 4 ms 的请求间隔，实际 Unix shell／系统调度会增加该间隔。本机窗口接受的终端尺寸为 113×40、缩放 2×，使用默认 Menlo 14 pt。没有更改 demo 的产品 UI。

标题宿主回调标记该次输出已经交付模型的时刻，父布局记录同代次，`onFrameComplete(Accepted)` 计算延迟。合并掉的中间输出不计作已显示样本，因此同时报告帧间隔和采样帧数量；不能仅由“最后一次交付到 Accepted”得出输出刷新频率。测试结束还确认最终闪烁文字已经接受，进程退出后等待 1.35 秒，要求没有新增帧。

| 指标 | 基线 `d990f72` | 移除输出等待后 |
| --- | ---: | ---: |
| 120 次交付中的 Accepted 采样帧 | 11 | 57 |
| 帧间隔 p50 / p95 / p99，ms | 99.54 / 100.96 / 100.96 | 16.66 / 17.19 / 18.73 |
| 模型交付到 Accepted p50 / p95 / p99，ms | 6.55 / 27.87 / 27.87 | 4.58 / 8.61 / 8.99 |
| 退出后的新增帧 | 0 | 0 |

原始指标见 [performance-window-frames.json](performance-window-frames.json)。这是一次本机窗口观测，显示输出已脱离约 100 ms 的节流；p95 帧间隔仍略高于 16.7 ms。起点在模型交付之后，**不包含子进程响应、PTY 读取和后台解析**；终点是提交被接受，不等同于显示器实际扫描到对应像素的时间。

## 行布局复用

文字、背景、下划线和链接片段改为行内坐标。相同行 ID、不可变 cell 内容、列数、网格尺寸、字体和颜色状态复用排版，滚动仅改变绘制平移。单个字符编辑重建对应行，光标移动不重建行；颜色／字体更新生成新资源。缓存默认保留最多 256 行、8 MiB 保守权重，按最近使用顺序局部淘汰。帧另持租约，淘汰和缓存关闭不会关闭旧帧仍使用的布局。该权重包含行、run、cell、链接及文字成本，不是 native RSS 或 GPU 显存硬上限。

相同四组测量见 [performance-row-cache.json](performance-row-cache.json)。每轮 192 帧，新建 384 行：每帧一行新日志和一个新的空白末行；此前每帧重建 40／80 行。预热后文字 shape 仍为 192 次，没有通过省略变化文字获得速度。

| 场景 | 复用前 → 后 p95 ms | 复用前 → 后分配 MiB | 复用前 → 后峰值 RSS MiB |
| --- | ---: | ---: | ---: |
| 120×40，1× | 1.798 → 0.878 | 684.4 → 96.5 | 80.3 → 63.0 |
| 120×40，2× | 2.220 → 1.302 | 684.4 → 96.5 | 88.0 → 71.1 |
| 240×80，1× | 3.629 → 1.473 | 1367.3 → 164.8 | 96.3 → 75.2 |
| 240×80，2× | 4.742 → 2.494 | 1367.3 → 164.8 | 128.4 → 107.9 |

复用前数据来自 `eb48aac` 的同一循环，复用后数据采于本次变更提交前，报告明确标记工作树有改动。新增测量包装器也在固定旧基线上单独运行验证。四项行缓存回归检查滚动／编辑／改色／resize、网格尺寸改变、LRU／超限、缓存及字体来源关闭后旧帧像素与光标片段；完整 UI 94 项通过。图像透明度测试实际发现固定网格与字体度量混用的问题，已修复并通过全套像素回归。

## 独立装饰的原生验证

`demo` 的 `TerminalNativeDecorationTest` 用真实窗口／PTY 验证选择、清除选择和纯 OSC 133 标记。稳定画面后的三次更新都进入 Accepted 帧，父容器 measure 次数保持不变；command 命中 API 在纯元数据帧接受后返回新命令。该用例在本机通过，和上述 CPU raster 基准分开记录。文字层、图片及行布局不因这些装饰变化重建；辅助功能文本保留同一字符串，只计算新选择的 UTF-8 偏移。补充离屏像素和代次测试后完整 UI 为 97 项通过。

| 场景 | 本次结果 | 验收检查 |
| --- | --- | --- |
| 10 万行历史、1000 个命中 | 完整扫描 24.78 ms；19 页，单页 p95 1.483 ms | 每页最多 65536 扫描步骤／128 命中；查询可取消，快照释放 |

历史搜索进程累计分配 621.0 MiB、峰值 RSS 233.4 MiB，包含填充 10 万行；带装饰重排为 6721.8／629.5 MiB。查询取消计时低于此次单调时钟采样分辨率，记录为 0 ns，不能据此宣称零耗时。纯核心扫描页测量用于记录工作量；生产异步 API 在独立 search worker 扫描，其并发／取消行为另有实际 worker 回归。

图形统一使用 120×40、8×16 logical 网格、1× 的 960×640 CPU raster。PNG 按 120×40 placement 缩放整幅 UHD；Sixel 保留原始像素尺寸并裁剪当前窗口，因此两者可见源像素数不同，不能用上述 p95 排名协议。字体固定为仓库 Fira Code、20 pt；这一组使用测试的固定网格，不作为实际窗口字体布局的对比。

| 图形场景 | 累计托管分配 MiB | 峰值进程 RSS MiB | 资源观测 |
| --- | ---: | ---: | --- |
| UHD PNG | 145.5 | 246.7 | 解码／传输 33.69 ms，首次准备及绘制 44.63 ms；缓存权重 69.21 MiB |
| UHD Sixel | 204.3 | 202.8 | 编码字符串在测试内生成；完整解析和首次绘制时间另存 JSON |
| 1024 placements | 585.6 | 67.1 | 分配含逐次创建 placement 的协议事务；稳定帧没有重复解码／准备 |

UHD 的完整 RGBA 等价像素为 31.64 MiB，Sixel 实际保留索引颜色面。`native_estimated_bytes` 是组件预算：每块按一份 native CPU 像素、可能的一份 GPU texture 及对象成本保守计费；**不是驱动报告的 GPU 显存**。本组 RasterSurface 在 CPU 绘制，不创建 GPU 渲染目标，也未取得独立 GPU 物理内存峰值。原生 `Image` 准备计数同样不冒充驱动 texture 上传遥测。每个场景清空缓存后权重归零、RIS 清掉 placements；擦除当前屏幕只裁去对应 Sixel 区域，不能用于断言屏外片段已释放。

窗口测试使用 `@Test(useProcess = true)` 后重新验证了基准采集：[隔离进程记录](performance-window-isolation.json)。同一 120 次 PTY 交付得到 58 个 Accepted 样本，交付到 Accepted 的 p95 为 9.37 ms，退出后 1.35 秒无新帧；测试子进程峰值 RSS 116.9 MiB，调度父进程 19.0 MiB。脚本按子进程结束、父进程结束的顺序分别记录 `runtime` 与 `runner_runtime`，不相加或以父进程代替绘制进程。原基线数据仍保留其实际测试方式。
